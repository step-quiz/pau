# procediments/ — animated step-by-step procedures

Small pages, inside the PAU site, that show a mechanical procedure (for now, from the *Anàlisi* block: the equation of the tangent line, relative maxima and minima, the growth/decrease table, six optimisation problems, six cubics determined from conditions, Bolzano's theorem with bisection, and the asymptotes of a rational function) as an animation in the style of Graspable Math. The student watches symbols move, merge and change, one step at a time, with a short explanation for each step. The data (the function, the point…) can be changed with arrows or through the address.

Principles: keep it simple, step by step, smooth, and **every line shown is a true equality** (checked automatically, see §7).

Student-facing text is Catalan; code comments are Catalan; this file is English.

Dependency order: `katex` → `mates.js` → `formules.js` → `dades.js` → `motor.js` and the procedure file. Plain classic scripts (no modules, no build step); each file is an IIFE that sets one frozen global on `globalThis`, so pages work from any static host and the pure files also load in Node.

A change of look goes to `estil.css`; of timing, to `TEMPS` in `motor.js`; of behaviour, to `motor.js`. All procedures follow.

`Motor.inicia(proc[, container])` fills the container (default `#procediment`) with header, board, player, step text, data editor and footer, and returns a frozen controller `{carrega(valors), salta(i), seguent(), pas, total, ocupat, valors}` (handy in the console and in browser tests). If KaTeX did not load it shows a message and returns `null`.

## 3. Procedure definition

A procedure is a frozen object:

| Field | Meaning |
|---|---|
| `titol` | Page title (`h1`). |
| `categoria` | `algebra`, `geometria`, `analisi` or `probabilitat` (colour and breadcrumb). |
| `files` | Number of board rows. |
| `perDefecte` | Default data, e.g. `{a3: 0, a2: 2, a1: -3, a0: 1, x0: 2}`. |
| `exemples` | Data sets offered as chips. |
| `titolEditor`, `notaEditor` | Editor heading and an extra sentence for its note. |
| `editor` | Rows `{etiqueta: TeX, camps: [{id, sufix: TeX, nom, min, max, signe: 'sempre' \| 'negatiu', atenua0}]}`; an empty array means fixed problems (no editor, no summary; the chips choose the data, and `nomExemple(v)` gives their plain-text labels). Every field is an integer with ↑/↓ arrows; `signe: 'sempre'` shows `+2`; `atenua0` fades the term when it is 0. |
| `valida(v)` | `null`, or a Catalan error sentence. |
| `llegeixAdreca(p)` | Address parameters (decoded strings) → `{valors}` or `{error}`. |
| `escriuAdreca(v)` | Data → address parameters (strings). |
| `enunciat(v)`, `resum(v)` | Statement (text with `$TeX$`) and one-line TeX summary. |
| `passos(v)` | The step list (§4). |

Only `passos` and `resum` are mandatory for the engine; the rest have fallbacks or are optional.

### Address format (recta tangent)

`recta-tangent.html?f=2x^2-3x+1&x0=2`

- For `creixement.html`, `f` may also be a quotient: `1/x`, `2x/(x+1)`, `(x^2+3)/(x-1)` (numerator and denominator with more than one term go in parentheses). It is rejected, with the reason, if the denominator is a number other than 1, if numerator and denominator share a factor, or if the domain or the critical points are irrational.
- `f` is written as a student would write it: `x^3-3x+1`, `x(x-5)`, `(x-1)^3`, `2x²−3x+1`, `0,5x`… It must be a polynomial of degree ≤ 3 with integer coefficients between −9 and 9 that depends on x. `x0` is an integer between −5 and 5. A missing parameter takes its default.
- The engine reads the query string itself: a literal `+` means plus (with `URLSearchParams` it would become a space). `%2B` also works.
- If the address is wrong, the page explains why (in Catalan) and shows the default example.
- When the student changes the data, the address is rewritten with `history.replaceState`, so it can be copied and shared.

## 4. Steps and keys

`passos(v)` returns an array of frozen steps:

```js
{
  files: ['TeX of row 0', 'TeX of row 1'],     // '' = empty row
  classes: ['', ''],                           // CSS class per row ('final' = highlighted answer)
  text: 'Explanation with $TeX$.',
  cursor:    {clic: 'k'} | {arrossega: 'k', fins: 'k2'},   // optional
  reanomena: {newKey: 'oldKey'},               // optional
  fusiona:   {newKey: ['oldKey', …]},          // optional
}
```

A row may also be **text** instead of TeX (e.g. a problem statement): `Formules.filaText(text)` (a string starting with `§`). The text may contain `$TeX$` and phrases `Formules.frase(key, text, mark)` (written `{{key|mark|text}}`): a keyed phrase moves, merges and can be dragged like a symbol; `mark` (`objectiu` and `avis` yellow, `condicio` green, `doble` green with a «×2» badge) highlights it (CSS `.marca-…`). `Formules.enunciatMarcat(text, mark)` turns a statement with `[id:phrase]` / `[id*:phrase]` into a text row: phrases get keys `E<id>1`, `E<id>2`…, `mark(id)` gives their current mark, and it returns the key of each id's main phrase (starred, or the first). Text rows wrap, keep a fixed text size and are left out of the board-width fit. A change of mark counts as a change (anticipation box and cross-fade), because the engine compares `className` too.

Build it with `Formules.guio(nFiles)`: set `g.files[i]` / `g.classes[i]`, call `g.afegeix(text, options)`, return `g.passos`. A step identical to the previous one (same TeX, same classes) is skipped, so optional steps («Calcula cada terme») need no special case. `g.completa(text)` appends a sentence to the last step when the board must not change (e.g. «l'equació no té solucions»).

### Keys

Every symbol that must be followed from one step to the next is written as `\htmlData{k=<key>}{<symbol>}` (helpers `Formules.clau`, `op` for binary operators, `rel` for `=`). A key matches `/^[A-Za-z][A-Za-z0-9]*$/` and is unique within a step (all rows together).

Polynomial helpers use a one-letter prefix `P` and the degree `n` of the term:

| Key | Symbol | Key | Symbol |
|---|---|---|---|
| `Psn` | sign | `Pcn` | coefficient (absolute value) |
| `Pvn` | x, or the value that replaces it | `Pen` | exponent |
| `Pmn` | multiplication dot | `Ptn` | value of a computed term |
| `PR` | value of the whole expression | `PA`, `PB`, `PQ` | `(`, `)` and `'` of `(…)'` |
| `PEn` | new exponent when deriving | | |

`membreEsquerre(L, …)` writes `f(x) =` with prefix `L`: `LF` name, `LP` prime, `La`/`Lb` parentheses, `LX` argument, `Lq` `=`. Use different letters for `L` and `P`. The tangent equation (row 0) uses keys `T…`, documented at the top of `recta-tangent.js`.

### 4.1 Solving «polynomial = 0»

`Formules.resolPolinomi(g, row, P, terms, firstText, firstOptions)` adds the steps that solve `terms = 0` (degree ≤ 2, integer coefficients, rational roots) on one row, the way it is taught: divide by a common factor (and make the leading coefficient positive); degree 1: move the constant, divide; `Ax² + Bx = 0`: take out `x`, split the product, solve the linear factor; `Ax² + C = 0`: `x² = k`, `x = ±√k`; otherwise the quadratic formula (substituted, discriminant, square root, split `±`). No real solution: the last caption says why. It returns the solutions in ascending order as `[{valor, clau}]`, where `clau` is the key of the number on the last row (to drag it elsewhere). `Mates.arrelsRacionals(terms)` tells beforehand whether the roots are rational (procedures reject irrational cases in `valida`).

### 4.2 Compact keyed notation: `Formules.marcat`

Long scripts written as data (e.g. solving a system) use `marcat(text)`: `⟦k:tex⟧` is the symbol `tex` with key `k`. If the text starts with `prefix: `, every key gets the prefix and the single bare `=` (outside `⟦…⟧`) gets the key `prefix + 'q'`. Contents `=`, `<`, `>` are written as relations (`rel`) and `+`, `-`, `\cdot` as operators (`op`). Example: `marcat('q4: ⟦a:a⟧ + ⟦b:(-3a)⟧ = ⟦r:-2⟧')` has keys `q4a`, `q4b`, `q4q`, `q4r`. It throws on unbalanced brackets, invalid keys or more than one bare `=`.

In `polinomi-condicions.js` each equation of the system keeps its prefix (`q1`…`q4` from the translation; `q5`, `q6`… for the new equations of the solving phase), so an equation moves from the work row to the system just by keeping its keys, and an in-place change of one term (`⟦c:c⟧` → `⟦c:0⟧`) morphs only that term.

### Transition semantics (`motor.js`, `creaPissarra`)

From step A to step B:

1. **Same key** in A and B (or `reanomena: {new: old}`): the same symbol. It moves to its new place (and size); if its content changes, the old one cross-fades into the new one.
2. **`fusiona: {new: [old…]}`**: the old symbols fly into the new one, which pops in.
3. Other old symbols fade out; other new symbols fade in. Unkeyed parts of the rows cross-fade.
4. **Cursor**: `{clic: k}` clicks the old symbol `k` before anything moves; `{arrossega: k, fins: k2}` grabs `k` and drags it to the new symbol `k2` (default: its pair or fusion target), with a box that follows it.
5. **Anticipation boxes**: in steps without a drag, light-blue boxes first mark every symbol that will change or vanish (symbols merging into the same target share one box), then follow them to their new place. Steps with boxes last longer (`TEMPS.pasAmbAvis`).
6. **Wrapped symbols**: a keyed phrase of a text row may span several lines (its `getClientRects()` has more than one fragment, typically on phones). A single-line ghost of it would be drawn at the paragraph's left edge, over other text, so a wrapped symbol (in A or in B) gets no ghost: it stays visible in its own layer (class `sense-fantasma`) and cross-fades with it. Its anticipation boxes are drawn per line fragment, and the cursor clicks or grabs its first fragment. Ghosts carry `data-de=<key>` (useful in browser tests).

Positions are measured on the real KaTeX output, so any TeX layout works. Rules that keep the animation meaningful (all checked by the tests): a renamed new key is not in A and its old key is not in B; a fusion source is in A and not in B and merges only once; cursor keys exist (`clic`, `arrossega` in A; `fins` in B); the first step animates nothing.

## 5. Engine features

- Player: restart, previous, play/pause, next; one dot per step (jump); speed (slow/normal/fast); keyboard Space (play/pause, except on a focused button), ← and →.
- Board font: largest size (30 px, 22 px on phones) at which the longest line of the whole procedure fits; refitted when the width changes or the fonts finish loading.
- Editor: ↑/↓ under each number, hold to repeat (stops at the limit); `valida` messages; regenerates the steps 350 ms after the last change and rewrites the address.
- `prefers-reduced-motion`: every duration × 0.35.
- Accessibility: buttons have Catalan labels; the step text is an `aria-live` region; KaTeX also outputs MathML; editor values are `spinbutton`s (arrow keys).

## 6. Adding a procedure

1. Create `nom.js` (copy the structure of `recta-tangent.js`): data limits, `valida`, address read/write, texts, `passos`, definition object. For fixed problems without editor, copy `optimitzacio.js` or `polinomi-condicions.js` instead: problems as data, `Dades.problemesFixos`, a statement row with marked phrases.
2. Reuse `Formules` helpers; add new generic keyed writers to `formules.js` (not to the procedure) when another procedure could use them.
3. Create `nom.html` (copy `recta-tangent.html`; change the title, description and the procedure script/global).
4. Add the procedure to `proves/comprova.js`: address cases, a data grid, the structural lint (`comprovaGuio`) and a truth check for every line.
5. Run the tests; open the page and play every example (desktop and phone width).
6. Update this README and the main `README.md`.

## 7. Tests

```
node procediments/proves/comprova.js
```

No dependencies (Node ≥ 16). It loads the pure files with `vm` and checks:

1. `mates.js` and `formules.js`: fractions, parsing (values and the Catalan error messages), polynomial round trips, both TeX writers.
2. Address of the tangent line: valid cases, every error case, and the round trip `escriuAdreca → llegeixAdreca` for all 130 302 valid functions.
3. Structure of every step list (rules of §4).
4. **Strict truth** of every displayed line, with exact rational arithmetic: each row is converted from TeX to plain text, parsed and evaluated with the true `f`, `f'` and `f''`. Identities are checked at 4 points, which proves them for polynomials of degree ≤ 3; `(…)'` is evaluated with the five-point formula, exact up to degree 4.
   - Tangent line: lines with `y` must hold on the tangent line and fail off it; the final line must be `y = …` without `f`.
   - `resolPolinomi`, for every `ax² + bx + c = 0` with coefficients in −6…6 and rational roots: every row must have exactly the same solutions as the equation (`o` = union, `±` = both values, an equation row = its own roots).
   - Growth table: row 0 is the domain (`ℝ − {roots of Q}`); row 1 holds identities with the true `f` and `f'` (rational identities are checked at 14 points, enough for the degrees involved); row 2 holds equations whose solutions are those of `Q = 0` (before the derivative appears) or of «numerator of `f'` = 0» (after), or a test value `… = v > 0` whose arithmetic and sign are checked; row 3 is the table: the header must be complete (points = critical points ∪ excluded points, ascending; `−∞`, `+∞` at the ends), and every filled cell must be right (sign of `f'` on each interval, `0` / `∄` at the points, arrows, `màx` / `mín` exactly where `f'` changes sign); row 4 lists the increasing and decreasing intervals. The final table must be complete. The address round trip is checked for every case.
   - Optimisation: the statement row is not an equality and is not evaluated; at the end it must contain phrases marked `objectiu` and `condicio` (and no other marks). The test file has its **own model** of each problem (function of two variables, the other variable from the constraint, first and second derivatives, domain, optimum), and the model's derivatives are themselves checked with finite differences. Rows: the function (two variables, or one after substitution), the constraint (true on the constraint curve and false off it), the domain (as written in the model), the derivatives, equations (written solutions must be zeros of `f'` and include the optimum; other equations must vanish at the optimum and nowhere else among sample points of the domain), chains of values, and the answer `v = …, w = …, f = …`. `π` is treated as an indeterminate: every row is checked for π = 3 and π = 22/7.
   - Asymptotes: own model (roots of Q by the test's quadratic solver; side signs of Q by the multiplicity of the root, i.e. the first non-vanishing derivative; AH by degrees; AO by polynomial division `P = Q·S + R`). Every expression inside a `lim` is turned into an exact rational function (an evaluator over polynomial pairs) and its limit at `±∞` computed by degrees; every line of the infinity and oblique rows must have both sides with the same limit (`x → ±∞` lines: the same at both ends); every lateral line `lim_{x→a^±} f = k/0^± = ±∞` is checked (a root of Q, k = P(a) ≠ 0, side sign, result sign); summary lines against the model; the infinity row is `destacat` exactly when there is no AH. 4 000 random cases cover AV+AH, AV+AO, AV only, AH only, AO only. 12 mutations detected (one caught a real bug: `Fraccio.de(a, b)` ignores `b`; use `new Fraccio(a, b)`).
   - Bolzano: the test file redoes the bisection itself (exact rationals) and checks every row: `f(x)` identity; the continuity row names `[a, b]`; `f(a)`, `f(b)` chains and their sign; the conclusion (exists / same sign); every table row (interval = the model's, with the true signs under the endpoints, which must differ; midpoint exact; `f(m)` exact, or with `≈` within half a unit of the last shown decimal, non-zero and with the right sign); the answer (`c ∈ (l; r)` of length `(b − a)/2ⁿ`, or `c = m` for an exact root). Grid: the examples and 3 000 random cases (with exact roots and same-sign cases); address round trip and errors; `decimal()` unit cases. 10 mutations detected.
   - Cubic from conditions: the test file has its **own model** of each problem (conditions `[order, x, value]` in statement order, conditions per phrase, stated extrema and inflections, solution), and also checks that the problem data say the same. Every row is turned into an affine form in `a, b, c, d` (evaluated on a basis and checked at two more points, so a non-linear row fails): while the system has fewer than 4 lines, line *i* and the work row must be **the same equation** as condition *i* (proportional forms); once it has 4 lines, the system must have a unique solution, equal to the model's (so every displayed system is equivalent to the original); work-row chains must hold at the solution; `f`, `f'`, `f''` and the answer are identities in `x` (for the general rows, at the solution and at two other parameter vectors); a check `f''(p) = … < 0` / `> 0` must be true. At the end: the system reads `a = …, b = …, c = …, d = …` with the solution, the answer is highlighted and has no letters left, every data phrase is marked (`doble` exactly when it gives two conditions), every stated extremum is real (`f'(p) = 0` and the sign of `f''(p)`, also ≠ 0 for «extrem») and has its `f''` check, and every stated inflection has `f''(p) = 0` with `a ≠ 0`. 16 mutations of the code and data are detected.
   - Extrema: rows 0–1 are identities (a final `< 0` / `> 0` is checked) or equations with exactly the critical points as solutions; rows 2–3 are a critical point `x = a`, or a conclusion checked with `f'(a) = 0`, `f(a)` and the sign of `f''(a)` (`f''(a) = 0` only for a cubic, where `f''' ≠ 0` proves it is neither); the last step has one conclusion per critical point. `valida` must reject exactly the irrational cases.

Grids: 10 052 tangent-line data sets, 1 344 equations, about 4 700 valid functions for extrema and about 4 200 for the growth table (dense, extremes and a fixed pseudo-random sample). The run takes about 35 s and ends with `Tot correcte: … comprovacions` (exit code 0) or the first errors (exit code 1).
